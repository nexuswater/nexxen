# Marqeta sandbox adapter — implemented, not connected

`adapters/marqeta-sandbox.mjs` implements narrow public-sandbox operations with mocked tests. No provider API was called during implementation. The user reports that their Marqeta account, 2FA and sandbox now exist in their own browser. No credentials have been captured or configured in this runtime. Cloud-browser access previously returned HTTP403. Do not bypass access restrictions or paste credentials into chat.

**Production bank/network program approval is not required merely to test the public sandbox.** Production launch is separate. The public quick start supports creating sandbox users/cards, loading a GPA from sandbox program funding and simulating an authorization. This does not mean Marqeta accepts RLUSD, receives AP4M testnet funds, converts currencies, or issues a spendable production card.

## Exact implemented API surface

Pinned base: `https://sandbox-api.marqeta.com/v3`. Only this verified public-sandbox URL is currently allowed; a different assigned sandbox requires explicit code review, not a relaxed arbitrary-host flag. Runtime Basic auth uses application token as username and admin access token as password. Secrets stay in private fields and are neither logged nor returned.

| Method | Documented endpoint | Adapter inputs / behavior |
|---|---|---|
| `createUser` | POST `/users` | `firstName,lastName` maps to `first_name,last_name`; separate setup authorization required |
| `listCardProducts` | GET `/cardproducts` | Returns only token/name/active; listing does not prove non-JIT configuration |
| `createCard` | POST `/cards` | `userToken,cardProductToken`; configured approved product only, no PAN/CVV query parameters |
| `loadSandboxUsd` | POST `/gpaorders` | `operationToken,userToken,amountUsd`; explicit resource `token`, numeric USD amount, fixed `sandbox_program_funding` |
| `getLoad` | GET `/gpaorders/{token}` | Reconciliation only; 404 reports absence, not permission to repeat POST |
| `authorizeSimulation` | POST `/simulations/cardtransactions/authorization` | Configured card/merchant/network and exact USD amount; no arbitrary webhook or destination |

The adapter does **not** retry POSTs. Persist operation tokens and intended payloads before calling it. A network timeout or unreadable response is an unknown outcome requiring reconciliation; never infer failure or safely replay from a timeout. Caller-supplied GPA resource tokens are source-supported, but this implementation makes no blanket claim about a generic `Idempotency-Key` header. Card creation also must not be blindly repeated: the quick start warns that later creations can terminate earlier cards.

## Gates and sanitized results

All calls require `enabled:true`, `approvedSandboxOperations:true`, pinned base URL, external runtime credentials and a bounded `maxUsdCents`. User/card setup additionally requires `setupApproved:true`. GPA loads and authorizations require `nonJitVerified:true` from verified selected-program configuration: default public-sandbox automatic JIT can authorize without the AP4M-triggered load and would invalidate the intended demonstration. This boolean is a trusted integration configuration gate, not proof generated by the adapter; no UI can toggle it. Actual non-JIT setup must be verified before enabling.

`loadSandboxUsd` validates returned token, user, amount, currency and funding source against its request. `getLoad` returns whitelisted fields for the durable receipt gate to compare with its bound expected user/amount. Results include integer `amountCents`, `currency`, resource token, state and response code; `verified:true` requires `COMPLETION`, response `0000`, USD and the expected sandbox funding source. Pending/declined responses do not prove funding. Provider error bodies, PAN/CVV, memos, bank details and response extras are not returned.

Authorization success means only a sandbox authorization. It always reports `settlementVerified:false` and `gpuDeliveryVerified:false`. The configured network must match the actual sandbox product; the official example uses VISA and is not evidence of Mastercard support. No merchant acceptance or broad card compatibility is inferred.

## User-local read-only connection setup (Node 24+)

Only after the user approves storing credentials locally and making this read-only check, run these steps **in the cloned project directory on the user's authorized machine**. The assistant has not run them, accessed the Mac or created a secret file.

1. Create a private local file **without overwriting an existing one**:
   ```sh
   [ -e .env.local ] || (umask 077; cp .env.example .env.local)
   chmod 600 .env.local
   ```
2. Open `.env.local` privately in a local editor, not chat/screenshare. Set:
   ```dotenv
   MARQETA_SANDBOX_READ_ENABLED=true
   MARQETA_SANDBOX_BASE_URL=https://sandbox-api.marqeta.com/v3
   MARQETA_APPLICATION_TOKEN=<applicationToken from your sandbox>
   MARQETA_ADMIN_ACCESS_TOKEN=<adminAccessToken from your sandbox>
   ```
   Replace placeholders locally. Do not put credentials in shell command arguments, chat, screenshots or Git. `.env.local` is **plaintext, not encrypted**; mode600 restricts filesystem access. It is gitignored, but ignore rules are not a security boundary. Exclude it and all other secret `.env*` files from manual ZIP/upload operations; only `.env.example` belongs in source delivery.
3. Run the explicit native env loader:
   ```sh
   node --env-file=.env.local scripts/sandbox-check.mjs
   ```
   Or, if credentials were already provided through an approved runtime environment/secret mechanism, use:
   ```sh
   npm run sandbox:check
   ```

The npm command reads **process environment only**; it does not automatically load any dotenv file. The explicit `--env-file` command loads exactly the named local file. `npm start` is unchanged: local simulation only, no implicit Marqeta connection or mutations.

The check uses one **GET `/cardproducts`** with Basic auth, pinned public-sandbox host, no redirects, no retries and a 15-second timeout. It prints only connection status and returned/active product counts—not credential values, product names/tokens, PAN/CVV or provider bodies. Read access is separately authorized by `MARQETA_SANDBOX_READ_ENABLED`; it does **not** set `approvedSandboxOperations`, create a user/card, load funds or authorize a charge.

A successful check means only that the sandbox catalog read worked. It does not verify a non-JIT product, AP4M funding, issuer authorization, settlement or GPU delivery. On HTTP401/403, stop and check assigned sandbox access/credentials in the official dashboard; do not bypass restrictions. If the assigned API URL differs from the pinned URL above, stop for explicit adapter review—do not change a hostname allowlist casually. Share only sanitized check output if help is needed.


## Next read-only step: inspect the selected product's JIT configuration

The user reports the authenticated catalog read succeeded locally (one active product, no mutations). The earlier `nonJitProductVerified:false` meant **not inspected**, not that JIT was proven enabled.

No reinstall is needed: place the standalone `scripts/sandbox-inspect-products.mjs` in the existing project and run:

```sh
node --env-file=.env.local scripts/sandbox-inspect-products.mjs
```

This performs only GET `/cardproducts`, using the existing private environment file. It emits product token/name, active state and the documented `config.jit_funding` enabled flags for payment-card, program and program-gateway funding, plus gateway `always_fund`. Funding-source identities and gateway credentials are omitted; only their presence is reported. Missing/invalid booleans stay `null`, not assumed defaults. Three explicitly false enabled flags establish `productNonJitConfigured:true` at **product level only**. Card overrides/effective configuration remain unchecked, and the script never sets runtime mutation or non-JIT approval flags. No POST, card creation, load or authorization is performed.

The paths are verified in the [official OpenAPI schema](https://raw.githubusercontent.com/marqeta/marqeta-openapi/main/yaml/CoreAPI.yaml) (`jit_funding_*_funding_source` schemas). If fields are absent, review the selected product detail rather than concluding automatic funding is disabled.
